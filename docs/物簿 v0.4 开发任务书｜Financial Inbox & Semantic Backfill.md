截至 v0.3，物簿已经拥有：

```text

Durable
Maintenance
Account Classes
Living Runway
Residence
Deposit
Receivable
Statistics

```

当前资金事实源已经统一为：

```text

```

账户余额、支出、收入、退款、转账等均建立在该事实层上。

当前 v0.3 已经可以完成：

```text
“钱进入系统以后怎么存”
“钱怎么统计”
“钱在哪里”

```

但仍然存在一个明显瓶颈：

```text
现实支付

```

目前中间仍主要依赖：

```text
人工告诉朝汐

人工补账
```

因此真正的问题已经从：

```text
“账怎么存”
```

变成：

```text
“账怎么自动进入系统，而且不能漏”
```

# 1. v0.4 核心原则

本版本遵守以下设计哲学。

## 1.1 金钱事实优先于语义完整

例如自动获得：

```text
2026-11-01 12:03
龙记澄海狮头鹅
¥20.00
微信零钱通
```

即使系统不知道：

```text
白切鸡盖饭
午餐
外食
```

也必须先保存。

禁止：

```text
“商品内容不知道”
→ 不记录
```

---

## 1.2 不完整 ≠ 无效

一笔只有：

```text
时间
金额
商家
支付渠道
```

的流水仍然是有效资金事实。

它可以：

```text
annotation_status = UNANNOTATED
```

但不能消失。

---

## 1.3 资金余额允许先对齐，解释以后补

资金系统不能依赖：

```text
“历史每一笔都必须完整”
```

才能维持正确余额。

允许：

```text
BalanceCheckpoint
ReconciliationAdjustment
UnexplainedDifference
```

保证：

> **账可以暂时不完整，但余额不能长期失真。**

---

## 1.4 自动数据源不能直接写 MoneyTransaction

以后：

```text
微信通知
支付宝通知
银行通知
CSV
短信
人工补录
```

都先进入：

```text
RawFinancialEvent
```

经过：

```text
Normalize
Match
Reconcile
```

以后，才能形成：

```text
MoneyTransaction
```

# 6. 支付渠道与资金账户分离

不要继续把：

```text
微信
支付宝
银行卡
```

全部塞进同一含义。

例如：

```text
微信支付
↓

```

应该表示：

```text
payment_channel = WECHAT_PAY
funding_account = 招商银行卡
```

而不是：

```text
account = 微信
```

# 7. 示例

现实：

```text
招商银行卡
通过微信
支付麦当劳 ¥32.50
```

Raw Event 可能来自微信：

```text
provider = WECHAT
capture_source = ANDROID_NOTIFICATION

amount = 32.50
merchant_raw = 麦当劳
payment_channel = WECHAT_PAY
```

同时银行通知：

```text
provider = BANK
capture_source = ANDROID_NOTIFICATION

amount = 32.50
funding_hint = 招商银行卡
```

```text
MoneyTransaction

amount = 32.50
merchant = 麦当劳

payment_channel = WECHAT_PAY
account_id = 招商银行卡
```

并保留：

```text
evidence = [
    wechat_event,
    bank_event
]
```

# 47. Checkpoint-aware Backfill

当一条迟到交易的时间：

```text
早于最近 BalanceCheckpoint
```

并且：

```text
它可以解释 checkpoint discrepancy
```

系统应：

```text
插入真实历史交易
+
生成 reconciliation compensation
```

保证：

```text
当前余额不变
```

同时：

```text
未解释差额减少
```


```text
MATCHED
```

# 74. 语义字段允许为空

数据库必须允许：

```text
category = NULL
item_name = NULL
meal_type = NULL
tags = []
```

不能：

```text
NOT NULL DEFAULT '其他'
```

把所有未知信息强行伪装成：

```text
其他
```

未知就是未知。

---

# 75. Unknown 与 Other 区分

明确：

```text
UNKNOWN
```

表示：

```text
系统不知道
```

```text
OTHER
```

表示：

```text
已经知道，但不属于现有分类
```

二者禁止混淆。

# 100. Codex 开发约束

1. 先 Audit 当前 v0.3。
2. `money_transactions` 继续作为唯一资金事实层。
3. 自动数据源不得直接写最终资金事实。
4. Raw Event 永久保留。
5. Unknown 不强行写 Other。
6. 未补全交易不得隐藏。
7. Reconciliation 必须可解释。
8. 一个现实交易可以对应多个 Raw Event。
9. 一个 Raw Event 不得重复形成多笔资金事实。
10. CSV 改为补漏 / 对账来源。
11. 朝汐负责语义，不负责余额守恒。
12. 后补 Purchase 不得再次扣款。
13. BalanceCheckpoint 必须支持迟到流水。
14. 所有关键写入继续使用幂等。
15. 不大规模重写 v0.3 已稳定领域代码。
