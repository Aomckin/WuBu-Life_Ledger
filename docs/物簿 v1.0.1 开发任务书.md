# 物簿 v1.0.1 开发任务书

**版本主题：Less Forms, More Life**

**开发基线：v1.0.0-rc.2 / Schema 16**

**目标：让日常操作变得足够简单，用户不用理解财务系统的内部结构。**

本版以交互瘦身为主，不新增复杂业务能力，不重构三个核心领域，不引入新服务。

## 一、核心原则

**用户只负责告诉物簿发生了什么，不负责填写完整的数据库对象。**

- 确定的事实自动保存。
- 可选信息允许为空。
- 有合理默认值的字段自动处理。
- 不能确定的资金账户不得猜测。
- 真正有风险的歧义才要求人工确认。
- 内部 ID、交易单号、来源类型、置信度、幂等键等字段不出现在普通表单。
- 高级操作可以保留，但不得占据日常操作入口。

## 二、P0：重做财务收件箱审核

当前 `financial.js` 的审核表单字段过多。

改成**根据问题类型展示不同的轻量操作**。

例如：

**账户无法确定：**

```text
便利店消费  ¥7.00
2026-11-01 18:00

这笔钱从哪个账户扣除？

[零钱通 ▼]

[确认]
```

**疑似重复：**

```text
午餐  ¥20.00

可能对应：
12:03  龙记  ¥20.00
12:06  某商户  ¥20.00

选择对应记录，或确认独立交易
```

**退款待确认：**

```text
到账  ¥14.50

可能退自：
11月2日  支出 ¥14.50

[确认退款关联]
```

用户不应手动填写交易 ID。候选记录必须可以直接选择。

只显示当前问题真正需要修改的字段。

原因字段改成自动生成审计原因，详细备注可选。

原始证据保持可查看，但默认折叠。

## 三、P0：让已经入账的流水可以轻松修正

当前页面主要提供原始证据审核和语义补全，缺少方便的已入账流水修正体验。

需要支持：

- 修改分类。
- 修改商品或消费说明。
- 修改商家展示名称。
- 修改备注和标签。
- 修正错误账户或金额。

前四项只更新语义，不修改资金余额。

涉及账户、金额、方向的修正，必须使用受审计的资金校正流程，保证余额、关联退款、检查点及历史证据正确。

**不允许简单地直接覆盖原始账单，也不能让资金修正悄悄改变账户余额。**

每次编辑应预填已有内容，保存时只修改用户实际调整的字段。

## 四、P0：每周同步简化

保留现有微信、支付宝及银行原生适配器，不重新开发解析算法。

目标流程：

```text
上传账单
    ↓
自动识别平台和已有账户映射
    ↓
自动预览及对账
    ↓
确认导入
    ↓
只处理真正的歧义
```

具体要求：

1. 记住此前确认的付款方式到账户的映射。
2. 相同平台、相同付款方式，下次默认沿用。
3. 修改映射后自动重新预览，避免重复点击。
4. 默认优先显示新增数、重复数、待确认数。
5. 完整流水明细默认折叠，需要时才展开。
6. 未补商品名称不算异常。
7. 交易方向、付款账户或退款来源不能确定时，进入待确认，不胡乱入账。
8. 正常流水不需要逐条人工确认。

映射规则应基于明确来源和账户身份，不允许仅凭金额、时间或相似商家猜测银行资金归属。

保留 v0.4 的幂等、跨源去重、原始证据和余额检查点机制。

## 五、P0：极简手动记账

普通收支默认只展示：

```text
金额：16.00
说明：晚饭
账户：上次使用的账户 ▼

[保存]
```

分类、商家、支出性质、标签等字段放入“更多选项”。

如果账户已有可靠默认值，直接预选。

如果用户没有确认资金账户，允许保存为待匹配的财务备忘或语义证据，不直接修改账户余额。

优先复用现有 SemanticEvidence 等能力，避免为简单输入开发新的复杂子系统。

提供清晰状态：

- 已入账。
- 待匹配。
- 需确认。

不允许将待匹配记录计入真实账户余额。

## 六、P1：物品操作同步瘦身

普通购入默认只显示：

```text
物品名称
数量
规格（可选）

[保存]
```

单位使用合理默认值，时间默认为当前时间。

位置、类型、商家、备注等可以展开填写。

耐用品的详细属性可以创建之后再补。

不要求任何付款账户或资金关联。

保持 Items 现有数据规则，不为了简化表单牺牲库存正确性。

## 七、P1：取消内部 ID 手工输入

关联资金流水时，提供交易搜索和候选选择。

支持按：

- 金额。
- 时间。
- 商家。
- 描述。

查找关联候选。

用户直接点击对应记录。

不暴露数据库 ID 输入框，除非进入高级调试模式。

## 八、P1：页面与文档减负

整理导航，把日常使用入口放在最明显的位置。

日常首页优先展示：

- 快速记录。
- 每周同步。
- 待确认事项。
- 账户余额。
- 常用物品。

低频管理与高级配置折叠到次级页面。

修正“购买会同时更新钱物”等已失效的旧文案。

同步更新 `AGENTS.md`，明确当前架构以 v1.0 独立事实源为准。

清理旧前端死代码、重复表单实现和已弃用的提示文字。

**不要为了清理文档额外创建一批新文档。**

## 九、验收标准

必须覆盖以下场景：

**A. 每周导入**

使用隔离数据库与脱敏原生账单，完整测试上传、Preview、Commit、重导、退款和待确认。

已确认的账户映射在下一次导入时自动恢复。

**B. 简单修正**

对于一笔已入账的便利店消费，用户可以只修改分类并保存。

不要求填写金额、账户、交易 ID、审计原因等无关字段。

金额和余额保持不变。

**C. 资金歧义**

对于账户不明确的流水，用户只需选择账户。

对于多个匹配候选，用户可以直接选择交易，不必复制 ID。

**D. 快速记账**

输入“晚饭 16 元”。

存在已确认的默认账户时可以直接记录。

账户未知时能够安全暂存，等待后续匹配，不虚构真实余额。

**E. 物品操作**

录入“无糖可乐 2 瓶”。

无需填写资金信息即可完成物品记录。

**F. 可靠性**

重新运行现有财务对账、余额、退款、库存、幂等和朝汐 SDK 测试。

实际数据库仅在备份后进行升级或验证。

任何 UI 改造不得改变既有资金事实的计算口径。

## 十、开发约束与交付

- 不新增手机采集端。
- 不增加新的 AI 推理依赖。
- 不重写 double-entry-generator。
- 不修改朝汐项目源码。
- 不重新拆分 Items / Finance / AI。
- 不为了少几个输入框引入复杂通用表单引擎。
- 不追求企业级配置能力。
- 尽量复用当前后端，确实缺少安全编辑能力时再补最小接口。

Codex 应优先完成 P0，验收后继续 P1。

最终只需要更新现有说明及一份简短验收记录。

**核心验收：用户能够处理日常收支与每周账单，而不必理解底层财务模型。**

> 复杂性可以存在于程序内部，但不能成为使用物簿的门槛。
