# 物簿 v1.0 开发任务书

**版本：** v1.0.0  
**主题：** Independent Domains  
**性质：** 领域解耦、架构整理、稳定性验收、正式版发布

**核心目标：**

将当前物簿拆分为三个职责清晰、能够独立演进的内部模块：

1. **Items：物品本体**
2. **Finance：金额与账户**
3. **AI Assistance：外部 AI 辅助**

模块之间通过少量稳定接口交互，不再直接依赖彼此的内部实现和数据结构。

保持单仓库、单进程、单 SQLite、现有启动方式。

**这不是一次微服务改造，而是一次降低日常开发复杂度的模块化重构。**

---

## 一、开发背景

当前 v0.4 已实现：

- 物品、库存、消耗和耐用品生命周期。
- 资金账户、交易流水、转账、退款与商家储值。
- Living Runway、居住支出、押金与代垫管理。
- 微信、支付宝及银行账单的周期性导入与对账。
- Financial Inbox、语义补全、余额检查点。
- 购买与资金流水的后补关联。
- 本地 AI 分析与朝汐工具接入。

但是，当前系统仍存在跨领域强耦合。

根据 v0.4 源码，典型问题包括：

| 现有操作 | 当前耦合 |
|---|---|
| `RecordPurchase` | 记录物品的同时扣除账户余额 |
| `AmendPurchase` | 修改物品记录时修正资金流水 |
| `DeletePurchase` | 撤销购买时补偿资金 |
| `AddMaintenance` | 维护耐用品的同时创建支出 |
| `DurableAction(sell)` | 售出物品的同时创建收入 |
| `GetPurchase` | 查询购买记录时读取资金流水 |
| `ItemCost` | 跨库存、维护、退款计算成本 |
| `create_purchase_from_transaction` | 从财务事件直接修改物品事实 |

这些设计曾经有助于实现钱物同步，但随着系统发展，导致局部修改需要理解大量跨领域逻辑。

v1.0 不再追求跨领域强一致。

新的原则是：

**每个模块只对自己的事实负责。**

## 二、最终架构

推荐采用以下逻辑结构：

```text
WuBu-Life_Ledger/
│
├── internal/
│   ├── items/
│   │   ├── domain/
│   │   ├── service/
│   │   └── repository/
│   │
│   ├── finance/
│   │   ├── ledger/
│   │   ├── accounts/
│   │   ├── statements/
│   │   ├── reconciliation/
│   │   ├── merchants/
│   │   └── service/
│   │
│   ├── aiassist/
│   │   ├── provider/
│   │   └── tasks/
│   │
│   ├── links/
│   │
│   └── httpapi/
│
├── tools/
│   └── wubu_tool/
│
└── ...
```

以上是**逻辑参考结构，不要求机械照搬**。

Codex 应审计现有源码后采用改动范围最小、依赖关系最清晰的组织方式。

不为了目录整齐重写已经稳定的业务逻辑。

### 目标依赖关系

```text
          REST / UI / Zhaoxi Tool
                    │
          Application Interface
                    │
       ┌────────────┼─────────────┐
       │            │             │
       ▼            ▼             ▼
     Items        Finance     AI Assistance
       │            │             │
       └────────────┴─────────────┘
                    │
               SQLite
```

重要约束：

- Items 不直接依赖 Finance。
- Finance 不直接依赖 Items。
- AI Assistance 不直接操作任何业务事实表。
- 跨领域关联由独立的 Links / Integration 层负责。
- `httpapi` 负责请求适配，不承担核心业务规则。
- SQLite 可以共用，但每张业务表必须有明确归属。

## 三、Items：物簿本体

### 3.1 职责

Items 负责回答：

> 我现在拥有什么？它们在哪里？处于什么状态？经历过哪些变化？

保留：

- Item、规格、数量和单位。
- 库存增减、消耗、开封、用完、丢弃。
- 消耗历史和库存预测。
- 耐用品品牌、型号、序列号、保修。
- 位置、收纳、遗失、找回、售出、报废。
- 维护历史。
- 物品购入、获取、处置事件。
- 物品匹配、别名及现有 Intake 结果应用。

### 3.2 移除资金职责

Items 不再负责：

- 创建 Expense / Income。
- 扣除或增加账户余额。
- 处理转账、退款与充值。
- 查询真实账户。
- 校验资金账户是否存在。
- 计算财务意义上的净支出。
- 自动补偿或撤销资金流水。

物品获取事件不再要求账户信息。

例如：

```text
Items.record_acquisition

item = 无糖可乐
spec = 2L
quantity = 2
location = 冰箱
```

只改变物品事实。

**不产生任何资金事件。**

### 3.3 购买记录调整

现有 `PurchaseEvent` 可保留原有 ID、历史和库存作用，但需要重新明确定位：

> 这是物品获取事件，而不是资金支付事件。

新写入路径只需要关注：

```text
event_id
occurred_at
merchant?
items
quantity
source
note
```

不强制包含：

```text
account_id
expense_nature
payment_method
payment_transaction_id
```

原有金额字段如果需要保留以兼容历史数据，应标记为历史快照或遗留元数据。

**不得继续作为 Items 的权威资金来源，也不得让新物品操作依赖这些字段。**

商品价格历史、总持有成本等财务统计应归 Finance；如界面仍需展示，可通过可选关联查询。

### 3.4 维护和售出

维护事件：

```text
Items.add_maintenance
```

只记录维护事实。

售出事件：

```text
Items.sell_item
```

只改变物品生命周期。

即使完全没有 Finance 模块，上述操作也必须成功。

## 四、Finance：金额账户模块

### 4.1 职责

Finance 负责回答：

> 我有哪些钱？钱从哪里来、到哪里去？哪些变化已经解释，哪些还没有？

完整接管：

- Account。
- MoneyTransaction。
- Income、Expense、Transfer、Refund。
- Adjustment、BalanceCheckpoint。
- RawFinancialEvent。
- ImportBatch、Financial Inbox。
- 微信、支付宝和银行账单导入。
- 对账、去重、迟到流水补偿。
- TransactionAnnotation、MerchantRule。
- PlannedCashflow、Living Runway。
- 押金、代垫、住房费用及其他财务约束。
- 商家储值及专属账户业务。

### 4.2 独立事实源

Finance 不得要求任何交易必须关联物品。

例如：

```text
Finance.record_expense

amount = 20.00
merchant = 龙记
category = 餐饮
```

交易可以正常提交。

即使：

```text
item_id = NULL
```

也完全合法。

### 4.3 保留 v0.4 对账能力

以下功能必须原样保留：

- 原生账单 Provider 与导入模板。
- CSV / XLSX Preview。
- Commit Token 与幂等提交。
- 原始证据与批次历史。
- 重复流水匹配。
- 多候选审核。
- 未补语义保留。
- BalanceCheckpoint。
- Checkpoint-aware Backfill。
- Financial Inbox。
- 朝汐按时间查询及语义后补。

**v1.0 不重写现有对账算法，不替换已固定的 `double-entry-generator`。**

### 4.4 商家账户内部模块化

不继续尝试建立可以描述所有商家玩法的超级账户规则。

保留统一的基础资金事实：

```text
Account
MoneyTransaction
```

商家特殊逻辑放在 Finance 内部。

例如：

```text
finance/
├── accounts/
├── ledger/
└── merchants/
    ├── prepaid/
    ├── membership/
    └── ...
```

不同商家允许拥有不同规则。

可能包括：

- 充值赠送。
- 本金和赠送金分别扣减。
- 特定商品限制。
- 储值过期。
- 次卡核销。
- 专属积分。
- 商家退款限制。

这些规则不要求统一抽象为一个复杂的通用规则引擎。

遵循：

**能复用基础流水就复用；确实不同的业务逻辑留在对应商家内部。**

v1.0 只要求确定模块边界和迁移现有规则，不要求提前实现尚不存在的商家功能。

## 五、AI Assistance：外部 AI 模块

### 5.1 定位

AI Assistance 是一个**可选辅助模块**。

负责调用外部模型，将文本、图片、音频等非结构化输入转换成可供业务模块处理的结构化建议。

不直接拥有 Items 或 Finance 的事实数据。

### 5.2 当前代码处理

重点审计：

```text
internal/ai/client.go
internal/media/processor.go
internal/httpapi/analysis.go
local-ai/
```

当前已有：

```text
Analyzer
Transcriber
```

等接口。

优先复用现有设计，不开发新的插件框架。

### 5.3 模块职责

AI Assistance 负责：

- AI Provider 配置。
- 模型 HTTP 请求。
- 超时、错误和结果解析。
- 图片输入准备。
- 音频转写调用。
- 输入长度与输出格式限制。
- 结构化建议返回。

业务模块负责：

- 解释建议的业务含义。
- 验证业务约束。
- 决定是否应用。
- 实际修改数据。

例如：

```text
用户上传商品照片
        ↓
AI Assistance
        ↓
提取商品名称、规格、数量
        ↓
Items
        ↓
校验与匹配
        ↓
确认后修改库存
```

### 5.4 AI 不直接操作数据库

禁止：

```text
AI 识别结果
     ↓
直接修改 items 表
```

也禁止：

```text
AI 识别结果
     ↓
直接修改 money_transactions 表
```

必须经过对应领域的公开写入接口。

### 5.5 可关闭运行

未配置任何 AI 时：

- 物簿正常启动。
- 物品管理正常运行。
- 财务管理正常运行。
- CSV 对账正常运行。
- 手动操作正常运行。
- AI 分析入口明确显示不可用。

AI 请求超时或失败时，原始输入和既有事实不得丢失。

### 5.6 朝汐与本地 AI 区分

`tools/wubu_tool` 是**外部 Agent 接口适配层**。

它不属于 AI Assistance 的内部模型实现。

朝汐可通过 REST 分别访问 Items 和 Finance。

不得把朝汐 SDK、人格系统、Planner、Memory 等内容引入物簿核心。

## 六、Links：可选关联层

### 6.1 设计目标

Items 和 Finance 都是独立事实源。

二者通过 ID 建立可选关联。

例如：

```text
Item Acquisition
ID = acquisition-001
```

```text
MoneyTransaction
ID = transaction-123
```

关联：

```text
source_type = ITEM_ACQUISITION
source_id = acquisition-001

target_type = MONEY_TRANSACTION
target_id = transaction-123

relation = PURCHASE
```

### 6.2 关联规则

- 关联可以为空。
- 一笔交易可以关联多个物品。
- 一个物品可以关联多笔不同用途的资金流水。
- 关联不能要求金额完全相等。
- 关联不改变任何一方的余额或库存。
- 关联失效不影响原始事实查询。
- 不因一方记录被撤销而级联删除另一方历史。

### 6.3 不引入复杂事件系统

不需要：

```text
Kafka
RabbitMQ
Event Bus
Saga Framework
Distributed Transaction
```

一个轻量关联服务和关联表即可。

允许存储在同一 SQLite。

**不建立新的跨领域强制外键。**

---

## 七、跨领域操作的新语义

这是本次重构最重要的行为变化。

### 7.1 买物品

原来：

```text
record_purchase
  ├─ 记录物品
  ├─ 增加库存
  └─ 扣除金额
```

现在：

```text
Items.record_acquisition
  └─ 增加库存

Finance.record_expense
  └─ 扣除金额

Links.link
  └─ 可选建立关联
```

三个动作彼此独立。

### 7.2 退款 / 退货

资金退款：

```text
Finance.record_refund
```

只影响资金。

物品退回：

```text
Items.record_return
```

只影响物品。

二者可关联，但不互相自动触发。

### 7.3 售出耐用品

```text
Items.sell_item
```

只修改耐用品状态。

```text
Finance.record_income
```

只记录实际到账资金。

即使售出时间和到账时间不同，也完全合法。

### 7.4 购买后补

保留 v0.4 的语义后补能力。

但是：

```text
create_purchase_from_transaction
```

需要改造为通过公开领域接口创建 Items 事实，再建立 ID 关联。

不得通过跨域数据库事务绕过 Items 的接口。

已有 MoneyTransaction 不得再次扣款。

### 7.5 部分失败

如果物品记录成功、资金记录失败：

```text
Items = SUCCESS
Finance = FAILED
```

不得撤销已确认的物品事实。

调用者必须得到明确的部分完成结果，并能使用稳定幂等键重试失败步骤。

不得返回笼统的“全部成功”。

**不要求跨模块原子性，但要求每个模块内部原子性和幂等性。**

## 八、数据库与 Store 解耦

### 8.1 保留 SQLite

不拆成两个数据库。

不引入 ORM。

不引入额外数据库服务。

### 8.2 表归属

Codex 必须先列出当前全部表，并分配所属领域：

```text
Items
Finance
AI / Intake Support
Links
Shared Infrastructure
```

每张业务表只能有一个明确的写入负责人。

### 8.3 Store 拆分

当前 `internal/store` 的统一 Store 承担了大量跨领域职责。

v1.0 需要将业务读写归入对应模块。

允许共用：

```text
SQLite connection
Transaction helper
Migration runner
Idempotency infrastructure
```

但不得出现：

```text
ItemsRepository
  → SQL 直接修改 money_transactions
```

或：

```text
FinanceRepository
  → SQL 直接修改 inventory_events
```

### 8.4 历史跨域字段

对于旧版本遗留的：

```text
purchase_event_id
expense_id
account_id
payment_method
```

等跨域字段：

- 不直接批量删除。
- 不改变已有事实 ID。
- 先审计是否仍承担外键或业务约束。
- 需要的关联迁入 Links。
- 无法安全迁移的遗留字段可以暂时只读保留。
- 新业务代码不得继续扩大对此类字段的依赖。

最终要求是**逻辑解耦**，不是为了形式上删除所有旧字段而损坏历史数据。

## 九、迁移与兼容

### 9.1 迁移基线

以当前仓库 v0.4 / schema14 为基线。

正式数据库不能用于开发测试。

先备份：

```text
data/wubu.db
```

以及实际需要的附件数据。

### 9.2 历史数据必须保留

覆盖：

```text
Items
InventoryEvents
PurchaseEvents
PurchaseRevisions
MaintenanceEvents
DurableEvents

Accounts
MoneyTransactions
RawFinancialEvents
ImportBatches
Annotations
BalanceCheckpoints
PlannedCashflows
Deposits
Receivables

IdempotencyRecords
SemanticEvidence
Attachments
```

实际表名以代码审计为准。

### 9.3 历史事实不重演

**迁移不能通过重新调用购买、扣款、库存增加等业务接口重建历史。**

必须使用安全的数据迁移过程。

不得因为迁移：

- 再次扣款。
- 再次增加库存。
- 再次创建退款。
- 再次生成维护费。
- 改写原始交易时间。
- 丢失 v0.4 的对账证据。

### 9.4 API 兼容

原有 v0.4 REST 与朝汐工具不能无提示改变语义。

特别是原来会同时修改钱物的接口：

```text
record_purchase
add_maintenance
sell_item
create_purchase_from_transaction
```

必须明确处理。

允许使用临时兼容适配层，但它只能调用新领域接口，不得直接绕过模块修改数据。

如果某接口语义发生不兼容变化，应新增明确接口、标记旧接口弃用，并同步迁移调用者。

不得把以前“会扣款”的接口偷偷改成“不扣款”而仍返回旧式成功结果。

### 9.5 Schema / OpenAPI

同步：

```text
OpenAPI
Python SDK / DTO
朝汐工具映射
前端调用
```

禁止出现前端正常但 Agent 调用悄悄失效的情况。

## 十、前端要求

v1.0 仍然是一个应用。

不做：

```text
物簿 App
财务 App
AI App
```

三个独立程序。

保留当前页面、导航及启动方式。

物品页面只以物品信息为主要内容。

资金页面只以账户和资金事实为主要内容。

跨领域价格或关联内容可以作为可选信息展示。

如果缺少关联，不应显示错误，也不应阻止页面加载。

现有：

```text
/weekly-sync
/financial-inbox
```

必须保留正常功能。

## 十一、反过度工程化约束

**本项目是个人生活工具，不是企业级平台。**

严格禁止为了模块化主动引入：

- 微服务。
- 多仓库。
- 多数据库。
- 消息队列。
- 分布式事务。
- 服务发现。
- 复杂 DI 容器。
- 通用插件生命周期系统。
- 通用事件总线。
- 过多接口与 DTO 转换层。
- 不存在实际使用者的抽象。
- 全面重写前端。
- 全面重写财务对账。
- 重新实现 `double-entry-generator`。

一项抽象必须有真实的边界价值。

**如果新增接口、文件和胶水代码的复杂度明显大于它消除的耦合，应选择更简单的实现。**

---

## 十二、Codex 开发顺序

### Phase A：v0.4 基线审计

先运行现有测试。

记录当前：

- 业务表及归属。
- 跨域函数调用。
- 跨域 SQL。
- 跨域外键。
- 跨域 DTO。
- 旧 API 语义。
- Agent 工具依赖。
- 数据库迁移状态。

识别当前直接耦合点，形成清晰改造清单。

### Phase B：明确接口契约

先定义 Items、Finance 和 AI Assistance 对外提供的最小接口。

不急于移动大量文件。

确保每个接口只暴露该模块真正需要的业务能力。

### Phase C：Items 独立

解除：

```text
RecordPurchase
AmendPurchase
DeletePurchase
AddMaintenance
DurableAction
```

中的资金写入依赖。

使纯物品操作不要求 Finance。

### Phase D：Finance 独立

解除 Finance 中对 Item、Purchase、Inventory 的直接修改。

保留 v0.4 资金、对账和语义补全能力。

### Phase E：Links

迁移可选关联关系。

改造购买后补、维护费用、售出资金等跨领域关联。

### Phase F：AI Assistance

## 十四、复杂度验收

除了功能正确，还要验证模块化是否真正降低开发复杂度。

### 14.1 依赖检查

建立简单的包依赖检查。

确保：

```text
Items 不导入 Finance 内部实现
Finance 不导入 Items 内部实现
AI Assistance 不依赖业务 Repository
```

允许共同依赖必要的基础类型或稳定接口。

### 14.2 局部修改检查

验证三个典型修改场景：

**场景一：** 修改库存消耗规则。

原则上只需要修改 Items 及相应测试。

**场景二：** 增加某个商家账户规则。

原则上只需要修改 Finance 内部对应商家逻辑及测试。

**场景三：** 更换 AI 模型适配方式。

原则上只需要修改 AI Assistance 的 Provider 及测试。

如果以上局部修改仍然需要大范围改动其他模块，应继续检查依赖边界。

### 14.3 不追求文件最少

模块可以拥有适当数量的文件。

但每个模块的入口、职责和依赖必须足够清晰。

目标是让开发者或 Codex 修改一个普通功能时，**主要阅读对应模块及其公开契约即可**。

## 十七、最终验收目标

v1.0 完成以后，系统应当满足：

```text
物簿本体稳定
    ↓
以后开发库存功能
只需理解 Items

金额账户稳定
    ↓
以后开发财务功能
只需理解 Finance

AI 辅助稳定
    ↓
以后调整模型和提取功能
只需理解 AI Assistance
```

跨模块需求通过少量明确接口完成。

不要求物品和金额始终对齐。

不要求所有记录都拥有跨模块关联。

不要求 AI 理解完整项目源码。

不要求开发者为每次小功能修改掌握整个系统。

### v1.0 最终原则

> **各模块独立拥有事实，以简单接口相互协作。**
>
> **通过降低局部开发的理解成本，让物簿保持小巧、可靠、易于长期维护。**

物簿 v1.0 不以工程规模、架构复杂程度或功能数量作为成功标准。

它的成功标准是：

**以后用户想到一个小功能，仍然可以轻松交给 Codex 开发，而不用担心牵动整个系统。**

这才是本次正式版最重要的交付成果。
