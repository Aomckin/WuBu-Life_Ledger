# 物簿 v0.1.1 Dogfooding 补丁任务书

> 目标：处理第一次由朝汐真实写入物簿后暴露出的接口层、数据语义与 Agent 使用体验问题。
>
> 本任务书**不包含**正在进行中的购买记录编辑 / 删除、数量单位拆分 UI、单位选项以及事务化改单等工作。

---

# 1. 本轮核心问题

第一次真实写入暴露出以下问题：

```text
1. 朝汐必须先知道 Item 是否存在
2. Item 不存在时高层购买写入直接失败
3. Agent Tool 参数层级仍然偏底层
4. 商品规格、购买数量、库存单位语义容易混淆
5. 金额字段之间缺少一致性检查
6. 商品名称缺少归一化 / Alias 机制
7. API 错误对于 Agent 来说不够“可行动”
8. 缺少针对真实错误案例的回归测试
```

本版本重点：

> **让朝汐只描述现实事件，不再承担数据库工作流。**

---

# 2. 高层购买接口必须自动 Resolve Item

当前问题：

```text
朝汐调用购买
↓
物簿查不到 Item
↓
返回 Item not found
↓
朝汐必须再调用创建 Item
↓
再重新购买
```

该流程禁止继续作为正常路径。

---

## 2.1 正确目标

朝汐只需要：

```text
record_purchase(...)
```

例如：

```json
{
  "merchant": "便利店",
  "total_amount": 5.5,
  "items": [
    {
      "name": "无糖可乐",
      "spec": "2L",
      "quantity": 1,
      "unit": "瓶",
      "unit_price": 5.5
    }
  ]
}
```

后端自动：

```text
Resolve Item
     ↓
存在
→ 复用

不存在
→ 自动创建
     ↓
PurchaseEvent
Expense
PurchaseItem
Inventory Change
InventoryEvent
```

---

# 3. Item Resolver

新增统一：

```text
ItemResolver
```

禁止 Purchase API、Consume API 等各自写一套查找逻辑。

建议匹配顺序：

```text
1. exact canonical name + spec
2. ProductAlias
3. normalized exact
4. 唯一高置信候选
5. 无候选 → 自动创建
6. 多个模糊候选 → 返回 ambiguity
```

---

# 4. 商品名称归一化

新增基础 normalize 能力。

第一版不需要 LLM。

至少处理：

```text
前后空格
连续空格
大小写
常见全角 / 半角差异
单位格式
数字规格格式
```

例如以下应尽量归到同一表达：

```text
无糖可乐2L
无糖可乐 2L
无糖可乐 2 L
无糖可乐 2000ml
```

但：

```text
2000ml ↔ 2L
```

若实现会明显增加复杂度，可先只做文本规范化，不进行单位换算。

---

# 5. ProductAlias

建立 Alias 机制。

例如：

```text
Canonical:
无糖可乐 2L

Aliases:
零度可乐 2L
无糖可口可乐 2L
可乐无糖大瓶
```

要求：

```text
查询 Item
购买 Item
消费 Item
库存调整
```

统一经过 ItemResolver。

不要只有购买接口能识别 Alias。

---

# 6. 商品规格与库存维度语义

当前第一次错误本质是：

```text
“2L”
```

同时可能被理解为：

```text
商品规格
库存数量
库存单位
```

三种完全不同概念。

因此内部模型必须明确区分：

```text
Product / Item
├── name
├── package_size
├── package_unit
└── inventory_unit
```

例如：

```text
name = 无糖可乐
package_size = 2
package_unit = L
inventory_unit = 瓶
```

购买：

```text
quantity = 1
unit_price = 5.5
```

最终语义：

```text
1 瓶
每瓶 2L
每瓶 ¥5.50
```

---

## 6.1 UI 是否立刻展示规格字段

v0.1.1 不强制全面重做 UI。

允许继续显示：

```text
无糖可乐 2L
```

但数据库和 API 层不要继续依赖：

```text
name = "无糖可乐 2L"
```

来承担所有规格语义。

# 7. Agent Tool Schema 简化

REST API 可以完整。

Agent Tool 不应该一比一暴露所有底层字段。

例如 REST 可以拥有：

```text
currency
source
external_id
confidence
package_size
package_unit
payment_method
...
```

但朝汐常用 Tool 建议压缩为：

```text
record_purchase(
    items,
    total?,
    merchant?,
    payment_method?,
    note?
)
```

Item：

```text
name
quantity
unit
price?
spec?
```

其余：

```text
默认值
时间
source
currency
created_at
```

由后端填充。

目标：

> **减少模型参数格式错误概率。**

---

# 8. Tool 参数容错

针对截图中出现的：

```text
模型生成的后续工具参数格式有误
```

检查物簿 Tool Schema。

重点排查：

```text
必填字段是否过多
nullable 是否过多
枚举是否复杂
对象嵌套是否过深
同义字段是否并存
金额是否存在多个容易混淆的字段
```

原则：

```text
Agent Tool Schema
应优先：
短
明确
少层级
少枚举
有默认值
```

---

# 9. Tool 与 REST 分层

不要为了方便直接：

```text
Tool Schema = REST DTO
```

允许：

```text
Agent Tool
   ↓
Adapter
   ↓
Domain Service
   ↓
REST / Store
```

例如：

```text
record_purchase_tool
```

内部转换成完整：

```text
PurchaseEventRequest
```

这样以后后端字段增加，不需要同步让朝汐多填十个参数。

---

# 10. 金额一致性校验

新增购买事件金额校验。

检查：

```text
quantity × unit_price
≈ subtotal

sum(subtotal)
≈ item_total

item_total
- discount
+ extra_fee
≈ total_amount
```

允许现实中的：

```text
优惠
满减
配送费
服务费
会员折扣
抹零
```

因此不是简单：

```text
不相等 → 拒绝
```

而应该分：

```text
VALID
WARNING
ERROR
```

---

# 11. 金额 Warning

例如：

```text
quantity = 2
unit = L
unit_price = 5.5
subtotal = 5.5
```

明显存在：

```text
2 × 5.5 != 5.5
```

返回：

```json
{
  "warning": {
    "code": "PURCHASE_AMOUNT_INCONSISTENT",
    "message": "item subtotal does not match quantity × unit price"
  }
}
```

Agent 可以根据 warning：

```text
重新检查
```

而不是错误数据直接悄悄进入数据库。

---

# 12. 规格 / 数量误判启发式检查

针对第一次真实错误增加轻量 heuristic。

例如：

```text
商品名 / spec 中包含 2L
quantity = 2
unit = L
```

且：

```text
total_amount == unit_price
```

则高度疑似：

> 商品规格被重复识别成了购买数量。

返回：

```text
SPEC_QUANTITY_CONFLICT
```

只作为 Warning。

不要做复杂 AI 判断。

---

# 13. API 错误返回标准化

目前：

```text
Item not found
```

对于 Agent 信息量太低。

统一错误结构：

```json
{
  "error": {
    "code": "ITEM_NOT_FOUND",
    "message": "Item was not found.",
    "retryable": false,
    "suggested_action": "create_or_resolve_item"
  }
}
```

但 Purchase API 正常情况下不应再返回此错误。

---

# 14. Ambiguous Item

例如：

```text
“可乐”
```

同时存在：

```text
无糖可乐 2L
无糖可乐 500ml
普通可乐 2L
```

不得随便选。

返回：

```json
{
  "error": {
    "code": "ITEM_AMBIGUOUS",
    "candidates": [...]
  }
}
```

候选至少提供：

```text
id
name
spec
unit
current_quantity
```

方便朝汐直接追问用户。

---

# 15. 自动创建策略

如果：

```text
没有任何合理候选
```

且操作为：

```text
Purchase
```

默认允许自动创建 Item。

如果操作为：

```text
Consume
Finish
Open
```

不存在 Item 时：

```text
不要自动创建。
```

因为：

```text
“喝了一瓶不存在的可乐”
```

通常意味着匹配失败，而不是应该创建库存为负的新商品。

---

# 16. 写入来源

所有物簿事件都应记录来源。

至少：

```text
manual
agent
import
system
```

朝汐写入统一：

```text
source = agent
```

以后方便：

```text
统计错误来源
排查 Agent 写错的数据
Dogfooding
```

---

# 17. Idempotency

如果当前版本还没有完整实现：

所有朝汐关键写操作补：

```text
Idempotency-Key
```

重点：

```text
record_purchase
consume_item
adjust_inventory
finish_item
maintenance
```

Agent 网络超时后重试：

```text
不得重复扣库存
不得重复增加库存
不得重复产生 Expense
```

---

# 18. InventoryEvent 完整性

确认所有库存变化路径都会写历史。

包括：

```text
Purchase
Consume
Adjust
Open
Finish
Edit Purchase
Delete Purchase
```

当前 Item.quantity 只是：

> 当前结果。

InventoryEvent 才是：

> 为什么变成这个结果。

禁止出现：

```text
quantity 改了
history 没变
```

---

# 19. PurchaseEvent 返回结果

成功写入后不要只返回：

```text
success
```

返回一份适合 Agent 理解的摘要：

```json
{
  "purchase_id": "...",
  "expense_amount": 5.5,
  "items": [
    {
      "item_id": "...",
      "name": "无糖可乐",
      "spec": "2L",
      "quantity_added": 1,
      "unit": "瓶",
      "inventory_after": 1
    }
  ],
  "warnings": []
}
```

这样朝汐能直接确认：

> 已记录无糖可乐 2L × 1 瓶，¥5.50。

不需要再调用查询接口确认。

建议增加：

```text
validate_purchase
```

或：

```text
POST /purchases?dry_run=true
```

输入购买事件后：

```text
Resolve Item
金额检查
规格冲突检查

```

但：

```text
不写数据库。
```

不是强制 P0。

如果实现简单，可以加入。

以后朝汐面对低置信度截图时：

```text
先 validate
↓
确认
↓
正式写入
```

# 21. Regression Case #001

将第一次真实错误正式写成回归测试。

测试名称建议：

```text
purchase_2l_bottle_must_not_become_quantity_2_liters
```

输入语义：

```text
商品：无糖可乐
规格：2L
购买数量：1
库存单位：瓶
价格：¥5.50
```

EXPECT：

```text
name = 无糖可乐
package_size = 2
package_unit = L

quantity += 1
inventory_unit = 瓶

Expense = 5.5
PurchaseItem.quantity = 1
unit_price = 5.5
```

禁止产生：

```text
quantity = 2
unit = L
Expense = 5.5
```

# 29. 最终验收

以下对话必须可以只使用一个高层工具完成：

```text
暗苟：
“刚刚买了一瓶 2L 无糖可乐，5块5。”
```

朝汐：

```text
record_purchase(...)
```

物簿内部：

```text
自动匹配 / 创建商品
↓
识别：
规格 = 2L
数量 = 1
单位 = 瓶
↓
校验金额
↓
写 PurchaseEvent
↓
写 Expense
↓
库存 +1
↓
写 InventoryEvent
```

返回：

```text
已记录：
无糖可乐 2L × 1 瓶
¥5.50
当前库存：1 瓶
```

全过程不得要求朝汐：

```text
先查询
→ 再建商品
→ 再购买
→ 再改库存
→ 再确认
```

> **朝汐负责理解人话，物簿负责把一件现实事件可靠地落地。**

不要让朝汐兼职数据库操作员。
