初次调研：2026-11-02；接入验收：2026-11-03（北京时间）。初次直接读取 GitHub README、实现和 LICENSE，随后按用户决定固定源码并实际调用上游 Provider / IR。验证使用公开原生样本与虚拟交易，未上传私人账单。

## 2026-11-03 · 已落地的接入决策

用户已确定使用 [double-entry-generator](https://github.com/deb-sig/double-entry-generator)。本文件中的候选比较保留为调研依据，当前选型不再悬而未决。

- 微信、支付宝各有专用原生文件上传入口，实际调用对应上游 Provider / IR。
- **保留所选上游版本的银行账单导入能力**，增加银行 / 模板选择入口，使用其原生 CSV / XLS / XLSX 等实际受支持格式；不能把银行实现裁掉或只留不可调用的包。
- 银行范围以接入时锁定版本的实际注册清单为准，包括上游已有建设银行、中国银行、工商银行、招商银行等国内银行，以及汇丰香港、BMO、TD 等模板；支持清单与样本验收状态分开维护。
- 固定上游版本，保留许可证和来源记录；在 Provider / IR 后接物簿证据、Normalizer、对账、Preview/Commit，不以 Beancount 文本代替原始证据。
- 新入口、依赖、ImportBatch、Preview / Commit、每周同步 UI 已实际落地并通过本地验收，详见 [交付记录](V0.4_DELIVERY.md)。固定版本为 `v2.16.0 + wubu.1`，源码位于 `third_party/double-entry-generator`，版本校验与本地补丁记录见其中 `WUBU_PATCHES.md`；许可证完整保留。

## 用户确定的产品范围

主要入口为“导入微信账单”和“导入支付宝账单”，同时保留“导入银行账单”（先选银行 / 模板）。各入口验证本平台原生表头和账单结构，不做任意 CSV 自动识别或用户列映射。不要求用户把 Excel 另存 CSV、改列名或整理成 Generic 模板。

已发现的原生数据格式：微信 XLSX、历史 CSV；支付宝手机端“用于个人对账”CSV（含 GBK 编码），网页端 TXT/不同导出结构应独立区分。压缩包中的账单数据文件无需格式转换；直接支持加密 ZIP 尚未实现，也不能据此宣称已经支持所有导出包装。

## 已选定：double-entry-generator

- 仓库：[deb-sig/double-entry-generator](https://github.com/deb-sig/double-entry-generator)。Go，许可证 [Apache-2.0](https://github.com/deb-sig/double-entry-generator/blob/master/LICENSE)。
- [微信 Provider](https://github.com/deb-sig/double-entry-generator/blob/master/pkg/provider/wechat/wechat.go) 分开读取 CSV 和 XLSX；XLSX 使用 excelize，适合作为当前 Go 项目的实现参考。
- [支付宝 Provider](https://github.com/deb-sig/double-entry-generator/blob/master/pkg/provider/alipay/alipay.go) 独立处理 GBK CSV。不是把支付宝强行当微信表头解析。
- 可复用经验：原生文件读取、平台字段结构、付款方式与外部单号保留、格式样本。
- 接入限制：其目标是生成 Beancount/Ledger，并不提供物簿的 RawEvent/幂等/检查点补偿。微信解析包含固定前导行数和工作表假设；支付宝默认后处理可能过滤退款及原交易。这些行为不能原样用于物簿的永久证据层。
- 已确定实际复用 Provider / IR；接入范围同时包含微信、支付宝和锁定版本已有银行 Provider。物簿继续承担资金事实与对账，保留原始证据，不复用其最终账本输出作为证据层。

## 候选二：china_bean_importers（字段与边界对照）

- 仓库：[jiegec/china_bean_importers](https://github.com/jiegec/china_bean_importers)。Python，许可证 [MIT](https://github.com/jiegec/china_bean_importers/blob/master/LICENSE)。
- [微信实现](https://github.com/jiegec/china_bean_importers/blob/master/china_bean_importers/beangulp/wechat/__init__.py) 使用 CsvOrXlsxImporter，以微信原生表头定位记录。
- [支付宝手机端实现](https://github.com/jiegec/china_bean_importers/blob/master/china_bean_importers/beangulp/alipay_mobile/__init__.py) 使用 GBK，保存交易单号、付款方式等；另有网页端模块。README 说明网页端导出缺付款账户，优先使用手机端个人对账文件。
- 适合对照：支付宝手机/网页格式差异、零钱通/银行卡/花呗等支付方式、不同状态与退款边界。
- 不直接复用的行为：部分未知方向会先按支出解释并加确认标签，其他分支有忽略记录行为；物簿必须先保留原始证据，将不确定项送审核，不能照搬推断结果。
- Python/Beancount 运行时不是当前 Go 服务的最小接入方案，优先作为样本与字段对照来源。

## 已确定的落地接口

1. 微信专用上传 → WeChatAdapter（XLSX/本平台 CSV）→ RawFinancialEvent。
2. 支付宝专用上传 → AlipayAdapter（本平台原生 CSV/明确的格式版本）→ RawFinancialEvent。
3. 银行入口选择 provider_code → BankStatementAdapter → 对应上游银行 Provider；清单以锁定版本为准，支持原生格式，不泛化猜测文件。
4. 三类来源之后共享 Normalizer、对账、ImportBatch、Preview/Commit；共享文件读取不等于共用平台业务解析。
5. 保留原文件摘要、原始行、表头/单元格与付款方式；退款、内部划转、坏行单列状态，不能悄悄丢掉。
6. 修复既有手工记录匹配重复扣款，并添加原生样本、退款、重导、坏行与检查点补偿集成验收。

当前已完成调研、技术选型、任务书同步、原生入口和依赖接入、隔离验收及先前的手机能力清理。后续遇到新导出版本应补充相应脱敏原生样本；不能用公开样本证明所有现行格式均已兼容。正式数据库、正式服务及朝汐环境未部署或改动。
