# 物簿 v0.2 开发任务书

> 项目：**物簿 Wubu / Life Ledger**
>
> 版本：**v0.2**
>
> 版本主题：**Possessions & Cashflow**
>
> 一句话目标：
>
> **东西有生命周期，钱有流向。**

---

# 0. 版本背景

v0.1 已完成物簿最核心的第一阶段闭环：

```text
现实购买
↓
PurchaseEvent
↓
商品 / 库存
+
金额记录
+
历史记录
```

经过数天真实 dogfooding 后，当前主要限制已经从：

```text
“能不能记进去？”
```

转向：

```text
“记进去以后，能不能真正管理我的现实状态？”
```

目前主要缺口：

```text
1. 耐用品还没有形成真正的独立生命周期体系

2. 金额记录仍然偏“消费日志”
   还不能回答：
   - 钱从哪个账户出去？
   - 现在各账户还有多少？
   - 转账怎么处理？
   - 退款怎么处理？
   - 本月到底花了多少？
   - 钱为什么和真实余额对不上？

3. 首页与查询能力仍然偏库存视角
   还没有形成真正的“个人钱物状态总览”
```

因此 v0.2 不再继续扩展零散购买功能。

本版本正式建设：

```text
Money Ledger
+
Durable Lifecycle
```

---

# 1. v0.2 核心结构

目标结构：

```text
                         朝汐
                          │
                    High-Level API
                          │
          ┌───────────────┴───────────────┐
          ↓                               ↓
     Money Ledger                    Item Ledger
          │                               │
    Account                        Consumable
    Transaction                    Durable
    Transfer                       Maintenance
    Refund                         InventoryEvent
    Adjustment
          │                               │
          └──────────── PurchaseEvent ────┘
```

其中：

```text
PurchaseEvent
```

继续作为现实购买事件的核心连接点。

# 3. 开发原则

---

## 3.1 不做专业会计系统

物簿服务个人现实生活。

不追求：

```text
复式记账
总账
会计科目
资产负债表
税务体系
企业财务
```

但必须保证：

```text
余额变化可追溯
转账不算消费
退款能够恢复资金
余额修正留下记录
```

---

## 3.2 State + Event Log

继续沿用 v0.1 已验证的模式。

物：

```text
Item.current_quantity
+
InventoryEvent
```

钱：

```text
Account.current_balance
+
MoneyTransaction
```

耐用品：

```text
DurableItem.current_status
+
DurableEvent / MaintenanceEvent
```

当前状态用于快速查询。

事件用于解释：

> 为什么它现在是这个状态。

---

## 3.3 Agent First

朝汐调用的是现实动作：

```text

transfer_money
record_refund
adjust_balance
add_maintenance
sell_item
retire_item
```

而不是：

```text

```

# 7. 金额方向约定

内部建议统一：

```text
amount > 0
```

表示绝对金额。

方向由：

```text
type
```

决定。

例如：

```text
EXPENSE 5.50
```

表示：

```text
账户 -5.50
```

```text
INCOME 5000
```

表示：

```text
账户 +5000
```

避免：

```text
type = EXPENSE
amount = -5.50
```

这种重复表达方向的设计。

如当前代码已有统一负数语义，则以真实代码为准，但必须全项目保持一致。

---

# 8. Account Balance

Account 应保留：

```text
current_balance
```

用于快速读取。

但：

```text
MoneyTransaction
```

才是余额变化事实来源。

每次交易：

```text
BEGIN

Create MoneyTransaction
Update Account.current_balance

COMMIT
```

禁止：

```text
直接 UPDATE balance
```

而不产生交易历史。

---

# 9. Expense 迁移

当前 v0.1 的：

```text
Expense
```

在 v0.2 中应逐步迁移至：

```text
MoneyTransaction(type=EXPENSE)
```

不要长期维持：

```text
Expense
+
MoneyTransaction
```

两套平行账目。

---

## 9.1 兼容策略

根据实际代码选择：

### 方案 A

直接迁移现有 Expense 数据。

### 方案 B

暂时保留 Expense 表作为兼容层，但所有新写入进入 MoneyTransaction。

最终必须只有一个资金事实来源。


# 50. Codex 开发约束

1. 先 Audit，后开发。
2. 不清空 v0.1 数据。
3. 不建立 Expense 与 MoneyTransaction 两套永久事实源。
4. MoneyTransaction 必须能解释 Account balance。
5. 所有余额修改必须留下事件。
6. 所有库存修改继续留下 InventoryEvent。
7. Transfer 不计入收入 / 支出。
8. Refund 与 Purchase 尽量关联。
9. Maintenance 与 MoneyTransaction 可关联。
10. Durable 不直接删除，用状态表达生命周期结束。
11. Agent 只调用高层现实操作。
12. 跨领域事件必须事务化。
13. Agent 写入继续支持幂等。
14. 不因为 v0.2 新模块而大规模重写 Stockroom。
15. UI 仍然是辅助层，不抢业务优先级。
