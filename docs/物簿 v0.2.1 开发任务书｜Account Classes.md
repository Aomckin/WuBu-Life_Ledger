# 物簿 v0.2.1 开发任务书

> 项目：**物簿 Wubu / Life Ledger**
>
> 版本：**v0.2.1**
>
> 版本主题：**Account Classes**
>
> 一句话目标：
>
> **区分“真正可以自由支配的钱”和“已经被锁进特定消费场景的钱”。**

---

# 0. 版本背景

物簿 v0.2 已完成 Money Ledger：

```text
Account
MoneyTransaction
Income
Expense
Transfer
Refund
Adjustment
Reconcile
```

当前资金唯一事实源为：

```text
money_transactions
```

余额缓存可以由全部资金事件重算，每条流水保留 before / after / delta。

现有账户系统已经可以表示：

```text
微信零钱
支付宝
银行卡
现金
信用卡
```

并支持：

```text
创建账户
默认支付账户
收入
消费
转账
退款
余额调整
余额核对
```

现有 Agent 高层工具也已经具备上述能力。

但经过实际使用发现：

> 所有账户不能简单视为同一种“余额”。

现实中至少存在两种完全不同的资金账户。

---

# 1. 新增账户一级分类

Account 新增：

```text
account_class
```

固定第一版枚举：

```text
STORAGE
CONSUMPTION
```

---

# 2. STORAGE：存储型账户

含义：

> 主要承担资金保存、转移和通用支付，可以在较广范围内自由支配。

典型账户：

```text
微信零钱
支付宝余额
银行卡
现金
```

例如：

```text
Account:
name = "微信零钱"
account_class = STORAGE
```

存储型账户中的余额属于：

```text
自由可支配资金
```

---

# 3. CONSUMPTION：消费型账户

含义：

> 资金已经预先锁定到某个商家、平台或消费生态，通常不能提现或只能在限定场景使用。

典型账户：

```text
奶茶店会员余额
理发店储值卡
健身房会员余额
校园卡
游戏平台钱包
门店储值账户
```

例如：

```text
Account:
name = "茶颜会员余额"
account_class = CONSUMPTION
```

其中的余额：

```text
仍然具有消费价值
```

但：

```text
不能与现金 / 银行卡余额等价看待。
```

---

# 4. Account Type 与 Account Class 分离

不要用现有：

```text
type
```

直接承担这个语义。

应保持：

```text
account_class
```

描述：

```text
资金使用边界
```

而原：

```text
type
```

继续描述：

```text
账户具体形态
```

因此：

```text
微信零钱
class = STORAGE
type = WALLET
```

```text
招商银行卡
class = STORAGE
type = BANK
```

```text
茶颜会员余额
class = CONSUMPTION
type = MERCHANT_BALANCE
```

如果当前账户 type 中不存在：

```text
MERCHANT_BALANCE
```

则新增。

不要把所有消费账户都硬塞进：

```text
WALLET
```

---

# 5. Account 新增建议字段

根据当前代码结构调整命名。

建议：

```text
account_class
merchant?
restricted
withdrawable?
expires_at?
```

v0.2.1 P0 只强制：

```text
account_class
```

以及消费账户需要的基础关联信息。

其余字段：

```text
withdrawable
expires_at
```

可以作为 P1。

---

# 6. Merchant Binding

CONSUMPTION Account 应允许绑定：

```text
merchant
```

例如：

```text
茶颜会员余额
→ merchant = 茶颜悦色
```

```text
某理发店储值卡
→ merchant = 某理发店
```

用途：

```text
1. 页面展示
2. Purchase merchant 自动推断
3. 查询某商家剩余储值
4. 后续统计会员账户使用情况
```

不要要求所有消费账户必须绑定商家。

例如：

```text
校园卡
```

可能对应整个校园生态。

因此：

```text
merchant nullable
```

---

# 7. 余额汇总重新定义

当前 v0.2：

```text
total_balance
available_balance
```

主要按照是否为信用卡账户进行区分。

v0.2.1 改为更明确的三层汇总。

---

## 7.1 liquid_balance

自由可支配余额：

```text
liquid_balance
```

默认包括：

```text
enabled
+
account_class = STORAGE
```

的真实资金余额。

信用卡语义继续遵守现有规则。

---

## 7.2 consumption_balance

受限消费余额：

```text
consumption_balance
```

包括：

```text
enabled
+
account_class = CONSUMPTION
```

账户余额。

---

## 7.3 total_value

可选总价值：

```text
total_value
=
liquid_balance
+
consumption_balance
```

但：

> UI 不应默认只显示 total_value。

否则用户会误以为所有钱都可以自由使用。

---

# 8. 首页显示方式

推荐：

```text
自由可用资金
¥3850.00

消费储值
¥273.00
```

而不是：

```text
总余额
¥4123.00
```

作为唯一主数字。

需要明确表达：

```text
3850 可以自由支配
273 已锁定在消费账户
```

---

# 9. 新增 Top Up 语义

会员储值不能简单视为 Expense。

新增高层现实操作：

```text
top_up_account
```

例如：

```text
“微信给茶颜会员充 100，到账 110。”
```

Agent Tool：

```text
top_up_account(
    from_account,
    to_account,
    paid_amount,
    credited_amount,
    note?
)
```

---

# 10. Top Up 数据语义

输入：

```text
from = 微信零钱
to = 茶颜会员
paid_amount = 100
credited_amount = 110
```

系统生成：

```text
微信零钱
TRANSFER_OUT 100
```

```text
茶颜会员
TRANSFER_IN 100
```

以及：

```text
茶颜会员
BONUS 10
```

最终：

```text
微信：
-100

茶颜：
+110
```

---

# 11. BONUS

MoneyTransaction 新增：

```text
BONUS
```

含义：

> 商家或平台赠送的、只能在受限账户中消费的价值。

例如：

```text
充 100 送 10
```

其中：

```text
100 = Transfer
10 = Bonus
```

BONUS：

```text
不计普通收入
不计普通消费
```

因为用户并没有真正获得：

```text
¥10 可自由支配现金
```

---

# 12. BONUS 限制

默认：

```text
BONUS
```

只允许进入：

```text
CONSUMPTION Account
```

除非后续出现明确需求，否则不要允许：

```text
银行卡 + BONUS
```

这类奇怪语义。

---

# 13. 充值不计消费

这是本版本最重要的数据规则之一。

例如：

```text
微信零钱 -100
茶颜会员 +110
```

此时：

```text
本月消费 += 0
```

不能：

```text
本月消费 += 100
```

原因：

> 钱只是从自由资金转成受限消费权，还没有真正消费商品或服务。

---

# 14. 实际消费时再计 Expense

后续：

```text
“会员余额买了杯 20 块的奶茶。”
```

产生：

```text
茶颜会员余额
110 → 90
```

以及：

```text
MoneyTransaction
type = EXPENSE
amount = 20
```

此时：

```text
本月消费 += 20
```

---

# 15. Cash Outflow 与 Consumption

为了避免统计语义混乱，建议明确区分：

```text
消费
```

与：

```text
自由资金流出
```

例如充值：

```text
微信 -100
```

在现金流层面：

```text
liquid cash outflow = 100
```

但：

```text
consumption expense = 0
```

因此未来统计允许：

```text
spending
cash_outflow
```

分开。

P0 不要求完整 UI，但内部语义不要混淆。

# 17. create_account

Agent Tool 建议：

```text
create_account(
    name,
    account_class,
    type?,

    merchant?,
    note?
```

```text
create_account(
    name="茶颜会员",
    account_class="CONSUMPTION",
    type="MERCHANT_BALANCE",
    initial_balance=0,
    merchant="茶颜悦色"
)
```

---

# 18. 默认账户

当前默认支付账户保存在：

```text
money_settings
```

购买时显式 account_id 优先，否则可使用默认账户。

v0.2.1 保持该机制。

但新增规则：

> 默认支付账户仍然允许为 STORAGE 或 CONSUMPTION。

不过如果默认账户是消费型：

```text
merchant binding
```

与购买商家明显冲突时，应返回 Warning。

例如：

```text
默认账户 = 茶颜会员
购买 merchant = 麦当劳
```

不应静默使用茶颜余额。

---

# 19. 消费账户商家校验

若：

```text
account_class = CONSUMPTION
merchant = 茶颜悦色
```

而购买事件：

```text
merchant = 肯德基
```

返回：

```text
ACCOUNT_MERCHANT_MISMATCH
```

默认作为：

```text
WARNING 或 ERROR
```

具体根据现有错误体系实现。

不要自动猜。

# 25. 余额减少 / 失效

```text

```

```text

```

```text
reason
```

```text

```

# 26. Existing Account Migration

当前数据库已有账户。

迁移新增：

```text
account_class
```

时：

> 默认全部设为 STORAGE。

理由：

```text
不猜用户真实账户性质
不改变现有余额统计语义
```

随后用户可手动把：

```text
校园卡
会员卡
储值余额
```

改为：

```text
CONSUMPTION
```

---

# 27. 修改 Account Class

提供：

```text
change_account_class
```

或现有 Account 编辑 API 支持：

```text
account_class
```

从：

```text
STORAGE → CONSUMPTION
```

或反向修改时：

```text
不得改写历史 MoneyTransaction
```

只改变：

```text

以及之后的余额汇总方式
```

---

# 28. 历史统计与 Class 修改

注意：

如果一个账户过去一直被视为 STORAGE，后来改为 CONSUMPTION：

```text
MoneyTransaction 历史不变
```

但历史时间点的：

```text
liquid_balance
consumption_balance
```

可能受当前分类影响。

v0.2.1 不需要做：

```text
Account Class 历史版本
```

接受：

> 汇总按当前账户分类解释。

在文档注明即可。

# 29. Credit Card

现有信用卡语义保持不变：

```text
信用卡为净余额
额度不计资金
```



默认：

```text
CREDIT_CARD
account_class = STORAGE
```

但：

```text
liquid_balance
```

是否包含信用卡继续遵守现有规则。

不要借 v0.2.1 重写信用卡模型。

---

# 30. Refund

退款规则保持现有实现。

当前退款会关联原 EXPENSE，累计退款不得超过原消费，并且转账与调整不计收入支出。

新增需要验证：

```text
消费账户退款
```

例如：

```text
会员余额购买 ¥20
↓
退款 ¥20
↓
退回会员余额
```

应：

```text
CONSUMPTION Account +20
```

并继续使用：

```text
REFUND
```

不改变 Account Class。

---

# 31. 消费账户退款到 Storage

现实中也可能出现：

```text
会员消费退款
→ 原路退银行卡 / 微信
```

因此 Refund API 不应强制：

```text
refund_account = original_account
```

允许显式指定退款到账账户。

默认仍使用原支付账户。

# 35. Top Up Atomicity

`top_up_account` 必须事务化。

例如：

```text
微信 -100
茶颜 +100
茶颜 Bonus +10
```

三个动作：

```text
全部成功
```

或：

```text
全部回滚
```

禁止出现：

```text
微信扣了 100
茶颜没到账
```

---

# 36. Top Up Idempotency

必须使用现有稳定幂等机制。

相同：

```text
Idempotency-Key
```

调用两次：

```text
只能充值一次
```

不能：

```text
微信 -200
茶颜 +220
```

---

# 37. Top Up 校验

至少：

```text
from_account != to_account

from.account_class = STORAGE
to.account_class = CONSUMPTION

paid_amount > 0
credited_amount >= paid_amount
```

对于：

```text
credited_amount < paid_amount
```

可能现实存在手续费。

因此不要绝对禁止。

更稳妥：

```text
credited_amount > 0
```

若：

```text
credited_amount < paid_amount
```

返回 Warning：

```text
TOP_UP_VALUE_LOSS
```

---

# 38. 无赠送充值

```text
schema N

```

```text
MoneyTransactions

Purchases
```

# 49. 完成定义

以下完整场景跑通，即视为 v0.2.1 核心完成：

```text
暗苟：
“微信给茶颜充100，送10。”
```

物簿：

```text
微信零钱
500 → 400

茶颜会员
0 → 110

实际资金转入：
100

会员赠送：
10

消费：
0
```

随后：

```text
暗苟：
“用茶颜余额买了杯20的。”
```

物簿：

```text
茶颜会员
110 → 90

本月消费
+20
```

随后询问：

```text
“我还有多少钱？”
```

系统可以明确区分：

```text
自由可用资金
+
受限消费余额
```

而不是把两种完全不同流动性的余额混成一个数字。
