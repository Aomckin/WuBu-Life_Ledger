# 物簿 v0.4 开发任务书

> **当前唯一 v0.4 开发与验收基准。2026-11-03 用户决策：**
>
> - 明确采用 [double-entry-generator](https://github.com/deb-sig/double-entry-generator) 作为原生账单解析基础，复用其 Go Provider / IR 能力；不是仅作为参考后重写一套解析器。
> - 提供“导入微信账单”和“导入支付宝账单”两个专用入口，分别接收平台原生文件；不做任意 CSV 自动识别或用户自定义列映射。
> - 微信直接接收原生 XLSX / CSV；支付宝直接接收所选上游版本支持的原生 CSV（包括对应的 GBK 编码）。不要求 Excel 另存 CSV、改列名或套通用模板。
> - **保留所选上游版本的银行账单导入能力**，提供银行账单入口：选择银行 / 账单模板，再上传该模板原生文件。不得只保留微信、支付宝而裁掉银行 Provider，也不得把保留银行导入推到“更多 Provider”后续范围。
> - 原生文件 → 上游 Provider / IR → 物簿 RawFinancialEvent → 预览 / 对账 → MoneyTransaction；原始证据永久保留，物簿负责余额守恒、幂等与迟到流水补偿。
> - 详细范围与验收见第 8、53、72、95 节，以及 [原生账单接入决策](V0.4_IMPORT_RESEARCH.md)。本任务书定义待开发要求，不代表代码已经接入。
> - [旧版 Financial Inbox 任务书](<物簿 v0.4 开发任务书｜Financial Inbox & Semantic Backfill.md>) 已废止；手机采集实现、工具、产物已撤除，不得恢复。

> 项目：**物簿 Wubu / Life Ledger**
>
> 版本：**v0.4**
>
> 版本主题：**Weekly Reconciliation & Semantic Backfill**
>
> 一句话目标：
>
> **平时允许账不完整，每周用正式账单把现实重新对齐，再由朝汐慢慢补全语义。**

截至 v0.3，物簿已经拥有：

```text

Living Runway
```

当前资金事实源已经统一为：

```text

```

账户余额、支出、收入、退款、转账等均建立在该事实层之上。

当前系统已经解决：

```text

钱怎么统计

```

现在真正的瓶颈变成：

```text

↓
如何稳定进入物簿
↓
如何避免漏账 / 重复
↓
如何逐步补全语义
```

# 1. v0.4 核心取舍

本版本明确：

```text
不开发 Android 自动采集端
不监听微信 / 支付宝通知
不处理后台保活
不追求实时自动记账
```

采用：

```text
日常：
朝汐 / 手工快速记录

每周：
微信原生账单（XLSX / CSV）
支付宝原生账单（CSV）
必要时银行原生账单（按所选模板支持格式）

↓

自动对账
自动补漏
自动去重

↓

朝汐语义补全

↓

余额核对
```

目标：

> **把每周维护成本压缩到几分钟，而不是为了实时性维护一个 Android 子项目。**

# 2. 核心原则

---

## 2.1 金钱事实优先于语义完整

例如 CSV 中只有：

```text
2026-11-01 12:03:03
龙记澄海狮头鹅
¥20.00
支出
零钱通
```

即使系统不知道：

```text
白切鸡盖饭
午餐
外食
```

也必须进入资金账本。

禁止：

```text
商品未知
→ 不记录
```

---

## 2.2 不完整不等于无效

一条流水只要确定：

```text
时间
金额
方向
来源
```

就已经具备保存价值。

允许：

```text
merchant = unknown
category = unknown
item = empty
tags = empty
```

但 MoneyTransaction 必须存在。

---

## 2.3 Unknown 与 Other 必须区分

```text
UNKNOWN
```

表示：

> 系统暂时不知道。

```text
OTHER
```

表示：

> 已经知道，但不属于现有分类。

不得把所有无法识别的记录强行塞进：

```text
其他
```

---

## 2.4 每周原生账单是正式补漏来源

CSV 的定位不再只是：

```text
导入数据
```

而是：

> **Reconciliation Source**

即：

```text
补漏
去重
确认
对账
```

---

## 2.5 余额是最终现实锚点

即使 CSV 仍然漏了某些：

```text
现金
消费账户
特殊退款
历史缺失
```

也必须允许通过：

```text
BalanceCheckpoint
```

重新锚定现实。

原则：

> **允许账暂时解释不完整，但不允许余额长期错误。**

# 3. 总体架构

```text
朝汐 / 手工快速记录
          │
微信专用入口（XLSX / CSV） ── double-entry-generator 微信 Provider ─┐
支付宝专用入口（原生 CSV） ── double-entry-generator 支付宝 Provider ┤
银行账单入口（选择模板）   ── double-entry-generator 银行 Providers ─┘
                                                               ↓
                                   原生文件 + Provider / IR → RawFinancialEvent
                                                               ↓
                                              Normalizer / Reconciliation
                                                               ↓
                                                    MoneyTransaction
                                                               ↓
                                     Semantic Annotation / BalanceCheckpoint
```

文件读取与平台解析复用上游；资金事实、幂等、证据链、购买后补和检查点补偿继续由物簿承担。

# 6. Provider

本版本：

```text
WECHAT
ALIPAY
BANK
```

银行使用明确的 `provider_code` 保存实际银行 / 模板身份，不得把所有银行退化为无法区分的 BANK。资金匹配使用 provider + provider_code + account_id + external_id，避免不同银行相同单号碰撞。

具体银行支持清单从所选上游固定版本的 Provider 注册表维护，保留该版本已有银行能力。UNIONPAY / OTHER 和上游尚未支持的新来源按后续任务增加；Generic 通用文件识别不属于产品入口。

# 8. 复用 double-entry-generator 的 Provider

选定依赖：[deb-sig/double-entry-generator](https://github.com/deb-sig/double-entry-generator)，Go module `github.com/deb-sig/double-entry-generator/v2`。

落地要求：

1. 接入时固定可构建的 release 或 commit，记录模块版本、上游来源、许可证与本地修补；禁止运行时随意跟随 latest。保留 Apache-2.0 许可证、版权和适用 NOTICE。
2. 实际调用或适配上游 Provider / IR，平台解析保持分离；不得重新造一套通用列猜测器，再把包名写成“已复用”。
3. 微信专用入口固定使用微信 Provider，支付宝专用入口固定使用支付宝 Provider；银行入口先选明确银行 / 模板再调用对应 Provider。上传错入口时给出明确格式错误。
4. 保留上游已有银行 Provider、对应文件读取依赖和模板选择能力。至少覆盖所选版本的建设银行、中国银行、工商银行、招商银行、中信银行、广发信用卡、交通银行借记卡、农业银行借记卡、汇丰香港、BMO、TD 等实际已注册模板；其余银行以锁定版本注册表为准，不能因 README 未列出而静默删除。
5. 原生 CSV / XLS / XLSX 支持以各 Provider 的实际能力为准，不要求用户另存或改表头；原始文件及行 / 单元格证据先完整保存，再映射 IR，不能仅保留上游过滤后的最终账本输出。
6. 上游默认退款过滤、固定前导行数、未知方向推断和静默丢行行为须在接入时调整，保留原始证据并转成物簿审核项。上游规则不获得直接修改物簿账户余额或创建库存的权限。

物簿适配层：

```text
WeChatAdapter → upstream wechat Provider
AlipayAdapter → upstream alipay Provider
BankStatementAdapter(provider_code) → upstream bank Provider registry
                         ↓
                 RawFinancialEvent
                         ↓
             共享 Normalizer / Reconciliation
```

### 原生格式与银行边界

- 微信：原生 XLSX 与历史 CSV，支付方式、原交易单号和原始商品描述保留。
- 支付宝：原生 CSV 的编码与格式版本由支付宝 Provider 处理，手机端个人对账优先；不能强行按微信格式读取。
- 银行：保留所选版本各模板支持的原生格式，通过银行入口可访问，而不是只留不可调用的源码。模板 / Provider 支持清单、已验证样本清单分别展示。
- 物簿当前资金事实仍为 CNY 整数分。外币行保留原币种与原始金额，作为待审核证据，不自动换汇或将外币数值当成人民币入账；本次不扩建多币种账本。
- 这里只导入已导出的银行账单，不连接网银、不抓银行凭证，也不引入股票 / 基金 / 加密货币 Provider。

# 95. Codex 开发约束

1. 先 Audit 当前 v0.3。
2. 不重写 MoneyTransaction。
3. CSV 不再直接无中间层写最终资金事实。

14. 不增加手机端项目。

16. 采用 double-entry-generator 并保留锁定版本已有银行账单导入，银行入口必须可用，不能只留包名或死代码。

# 101. 原生入口与银行能力验收（2026-11-03 补充，P0）

1. 微信原生 XLSX、CSV 通过微信入口直接预览、提交；支付宝原生 CSV 通过支付宝入口直接预览、提交，不需另存、改列名或手工粘贴模板。
2. 两个入口各自调用 double-entry-generator 对应 Provider；用代码调用与集成用例证明复用，不能只以依赖出现在 go.mod 为通过。
3. 银行账单入口可以选择锁定版本提供的银行模板，注册 / 支持清单不得遗漏该版本已有银行 Provider；每个列为“已支持”的模板有原生格式样本解析测试，至少一个银行样本贯通 Preview → Commit → 再导入不重复记账。
4. 微信 / 支付宝和银行重复反映同一资金事件时，已确认同一账户与身份的只关联证据；不同银行相同单号不误合并，账户不明或匹配歧义进入 Review。
5. 原始退款、内部划转、坏行、外币行均有可查询证据和明确处理状态，上游预处理不能让其从导入报告中消失。CNY 迟到流水经过现有检查点补偿后余额保持正确。
6. 错入口或不支持的模板明确报错；不回退到任意 CSV 猜测，不暗中自动创建账户或换汇。
7. 文件摘要、批次、原始证据、匹配结果及确认回执可追踪；金融事实与库存仍遵守既有原子性和幂等约束。

以上是本版完成条件。真实银行样本缺失时明确列为未验收，不能把上游宣称支持当作本地已通过。
