## 实际落地

1. 固定 `double-entry-generator/v2 v2.16.0 + wubu.1`，实际调用微信、支付宝及银行 Provider / IR；固定源码、全部银行包、许可证及补丁记录在 `third_party/double-entry-generator`。上游 Windows 文件句柄泄漏已修复，浦发开放逐行转换并保留源单号。不是仅声明依赖或读取最终 Beancount 文本。
2. schema14 增加 ImportBatch、原始文件 BLOB / SHA-256、逐行批次回执、账户映射、同步轮次与索引。原始行、字段、时间精度、币种、付款方式和外部单号均保留；原文件可下载。迁移保留旧资金、库存、幂等回执，不伪造历史原始证据。
3. Preview 使用真实对账事务后回滚；Commit 必须携带预览 token 与稳定 Idempotency-Key。文件、账户映射或账本变化后需重新预览。原文件、证据、链接、资金事实、批次回执共用事务；失败全部回滚，网络未知回执可用原键重试。
4. 分开新增、匹配已有、重复、冲突、跳过、未补全。坏金额 / 时间逐行送审核，不阻断其他有效行；错平台、损坏文档、超限文件明确拒绝。每文件 5 MiB / 2000 数据行。失败 / 关闭 / 零金额记录仍保留证据并明确跳过。
5. 修复不同商家名称的手工记录匹配：12:05“午饭20”与 12:03“龙记20”复用同一资金事实。多候选不自动选择第一条；不同银行同单号隔离，无单号同秒同价两行仍独立。同文件换账户重导不能再扣一次。
6. 独立 Annotation、SemanticEvidence、附近交易默认 ±30 分钟、未补全查询、商家归一化与用户确认规则已贯通。可信分类 / 性质镜像到旧统计元数据；语义补全不改金额和余额。Agent 描述明确图片 / 聊天时间选择、多候选不猜、无候选只留语义证据。
7. BalanceCheckpoint、Unexplained Difference 与迟到流水反向补偿有效；历史退款 +22 可解释检查点差额，当前余额仍为 1320.50。Account Health 和每周同步汇总提供账户核对入口。
8. Purchase Backfill 复用既有支出，在同事务创建 PurchaseEvent / 库存事件，不再次扣款；失败及重复调用有回归。
9. 每周同步 UI 提供付款方式映射、预览 / 提交、逐行状态、整文件重复提示、分页历史、原件下载、按来源汇总、本轮持久化与新一轮。汇总不受历史列表 500 条上限截断，未补全按资金事实去重。
10. OpenAPI、生成脚本、本仓库 SDK 契约同步。Docker 在依赖下载前复制固定上游源码；Linux amd64 / CGO=0 交叉构建通过，本轮未执行容器启动验收。

## 明确边界与后续

- 本地开发与隔离验收已完成；未宣称正式部署、真实朝汐模型行为或未来所有银行导出版本均已验收。银行测试使用所锁定版本的公开原生样本，不是用户各银行账户的私人账单。
- 仅 CNY 可自动形成资金事实。外币保留币种与原始金额，审核时须明确人民币金额，不自动换汇。BMO / TD 的公开样本主要为外币，测试确认保留审核且不虚构 CNY 流水。
- 银行只有日期时保留 DAY 精度；与余额检查点同一天无法确定先后时送审核。退款须唯一定位同源原支出并校验可退余额；还款 / 内部划转需明确双方账户或关联已有转账，不从金额猜测。
- 不支持直接解密 ZIP；使用从官方导出压缩包解出的原始数据文件。超出固定模板的格式明确报错。已提交但待确认的原始行在 Inbox 处理，重导文件不会替用户覆盖审核结论。
- P2：Annotation Split、批量 Agent Annotation、新增上游未支持 Provider、更复杂对账、Data Completeness、规则推荐。任务书第89节建议的通用 reprocess_raw_event 未作为 P0 / P1 必需项实现。
- 原手机子项目、通知采集、设备接口、模拟器与 APK 已撤除，不纳入版本验收。已有历史证据 / 资金数据没有因撤除而清空。
- 保留原有未提交工作；未混合提交或推送。朝汐整个项目只读，所有适配改动均位于本仓库。施工资料库在当前写入范围外，未更新；可同步摘要：新版v0.4 P0 / P1本地验收完成，固定上游v2.16.0，微信 / 支付宝 / 14银行原生导入、语义后补、检查点补偿已贯通，正式环境未部署。
