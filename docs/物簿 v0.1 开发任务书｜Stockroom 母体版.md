# 物簿 v0.1 开发任务书

> 中文名：**物簿**
>
> 英文工作名：**Life Ledger**
>
> 定位：由朝汐（Zhaoxi）主要操作的个人钱物生命周期数据库。
>
> 核心目标：
>
> **一次现实事件，同时更新钱、物、库存与历史。**

---

本项目不从零开发。

> **以 Stockroom 为母体进行定向魔改。**

# 1. 项目核心定义

物簿不是：

```text
传统记账软件
资产管理软件
家庭 ERP
财务软件
库存 ERP
```

物簿是：

> **用于记录个人现实世界中“钱和物发生了什么”的长期数据库。**

需要回答的问题包括：

```text
今天买了什么？
花了多少钱？
在哪里买的？
现在还有多少？
什么时候买的？
上次多少钱？
这个东西用了多久？
什么时候开封的？
什么时候用完的？
修过几次？
一共花过多少钱？
东西现在还在不在？
```

---

# 2. 与现有个人系统的边界

现有结构：

```text
朝汐 Zhaoxi
     │
     ├── Life HUD
     │      ↓
     │   我做了什么
     │   当前状态
     │   任务 / 行动 / 日程 / 生活状态
     │
     └── 物簿 Life Ledger
            ↓
         我拥有什么
         我买了什么
         花了什么
         还剩什么
         东西经历了什么
```

朝汐是主要交互入口。

因此：

```text
朝汐 = 智能层
物簿 = 数据与业务层
```

禁止把复杂 LLM Prompt、人格、Agent Planner 等逻辑塞进物簿。

# 4. 总体设计原则

---

## 4.1 Agent First

主要入口：

```text
暗苟
 ↓
朝汐
 ↓
物簿 API
 ↓
SQLite
```

UI 的优先级低于 API。

优先级：

```text
业务数据正确性
>
Agent API
>
现实事件模型
>
查询能力
>
纠错 UI
>
统计 UI
>
视觉美化
```

---

## 4.2 Event First

现实发生的是：

```text
买东西
喝掉东西
开封东西
弄丢东西
修东西
卖掉东西
库存发现不对
```

而不是：

```text
INSERT item
UPDATE stock
INSERT transaction
```

因此对 Agent 暴露的主要接口必须以现实事件为中心。

---

## 4.3 一个事件统一钱和物

禁止：

```text
朝汐先记账
↓
再加库存
↓
再创建商品
↓
再写价格
```

这种由 Agent 连续调用多个底层 CRUD 的方式。

应该：

```text
record_purchase_event()
```

一次调用完成。

---

## 4.4 数据库事务

凡是一个现实事件会改多张表：

```text
必须使用 Transaction
```

例如：

```text
PurchaseEvent
+ Expense
+ PurchaseItem
+ Inventory
+ InventoryEvent
```

必须：

```text
ALL SUCCESS
```

或者：

```text
ALL ROLLBACK
```

禁止半套状态。

# 16. record_purchase_event 内部逻辑

要求：

```text
BEGIN TRANSACTION

Create PurchaseEvent

Create Expense

FOR EACH PurchaseItem:

    Resolve Item

    Create PurchaseItem

    IF CONSUMABLE:
        Increase quantity
        Create InventoryEvent(PURCHASE)

    IF DURABLE:
        Create / Link Item
        Create DurableDetails

COMMIT
```

任何步骤失败：

```text
ROLLBACK
```

---

# 17. 金额校验

允许：

```text
sum(items.subtotal)
```

与：

```text
PurchaseEvent.total_amount
```

存在小差异。

因为现实存在：

```text
优惠券
满减
配送费
服务费
抹零
会员折扣
```

建议：

```text
item_total
discount
extra_fee
total_amount
```

v0.1 至少不要强制：

```text
sum(items) == total
```

否则真实账单会频繁失败。


# 25. Intake 改造方向

Stockroom 自带 Intake 很有价值。

但物簿的智能主体不是 Stockroom 内置 AI，而是：

```text
朝汐
```

因此优先：

```text
保留 Intake 数据结构 / Review 流程
弱化 Stockroom 自带 AI
```

未来推荐：

```text
图片 / 小票 / 截图
      ↓
    朝汐
      ↓
结构化 Purchase Draft
      ↓
   Intake Review
      ↓
PurchaseEvent
```

如果暗苟明确确认：

## 必须遵守

6. 不为了技术漂亮增加抽象层。
7. 不创建没有实际用途的接口。
8. 不提前实现 v0.2+ 功能。
9. 所有多表现实事件使用事务。
10. 所有 Agent 关键写入考虑幂等。
11. 所有 Agent 能力优先暴露 REST/OpenAPI。
12. 所有数量变化必须可追溯。
13. 删除能力前先确认没有后续复用价值。
14. 不直接大段复制其他仓库代码，只参考设计。
